# startlocal

Scripts to run the whole Poly+ stack on this Windows machine, one script per
zone. The upstream dev scripts are bash and assume Homebrew (`pg_ctl`, `jq`,
`zip`), so they cannot run here.

```powershell
powershell -ExecutionPolicy Bypass -File .\startlocal\start-all.ps1
```

Every script takes `-Stop`. Run them individually when you only want one zone.

## Zones

| Script | Port | What it is |
| --- | --- | --- |
| `postgres.ps1` | 5432 | Postgres in Docker, database `local`, with `pg_trgm` |
| `s3.ps1` | 8081 | rclone serving `.local/s3` as S3; `-Seed` writes the dev objects |
| `render.ps1` | 8090 | skinview3d sidecar that renders cosmetic covers |
| `backend.ps1` | 8080 | the Poly+ API; docs at `/scalar` |
| `seed.ps1` | — | applies `seed.sql` |
| `store.ps1` | 3001 | `plus-website`, the shop (Next.js) |
| `dashboard.ps1` | 3000 | `plus-admin-dashboard` (Vite) |
| `backend1.ps1` | 8082 | `backend-1`, the maven/update-check API |
| `launcher.ps1` | — | OneLauncher desktop app |
| `mod.ps1` | — | publishes the OneConfig modules to `~/.m2` |
| `polyplus.ps1` | — | builds PolyPlus, the cosmetics mod behind the in-game store |
| `status.ps1` | — | what is up, plus a live API check |
| `stop-all.ps1` | — | stops everything this folder started |

`start-all.ps1` runs the services in dependency order and skips the two that are
not services: pass `-WithLauncher` for OneLauncher, `-WithBackend1` for
`backend-1`. `mod.ps1` is a build, not a service, so run it on its own.

## Prerequisites

- Docker Desktop, running
- Rust (`cargo`), Node, npm
- rclone — `winget install --id Rclone.Rclone -e`
- Chrome or Edge, for the render service. Puppeteer's own Chromium download is
  skipped in favour of whichever is installed.
- Visual Studio C++ build tools, for OneLauncher only

## Ordering, and why it matters

The backend applies its migrations at startup, and the seed needs the schema
those migrations create, so the order is Postgres → S3 → render → backend → seed.
`start-all.ps1` already does this. Seeding before the backend's first run fails
on a missing table, and `seed.ps1` says so rather than leaving you to guess.

## Configuration

The backend reads `plus-backend-main/.env`. Two things there matter locally:

- `DATABASE_URL` needs credentials for the Dockerised Postgres:
  `postgresql://postgres:postgres@localhost:5432/local`
- `CORS_ORIGINS` must list both front ends, `http://localhost:3000` for the
  dashboard and `http://localhost:3001` for the store, or the browser blocks
  every request and the pages look broken for no visible reason.

`backend.ps1` passes these to the backend as command line flags rather than
environment variables. Several are required flags with no fallback but are empty
in a local `.env`, and assigning an empty string to `$env:X` on Windows deletes
the variable rather than setting it, which makes the backend refuse to start.

The store reads `NEXT_PUBLIC_BACKEND_URL` from `plus-website/.env.local`, which
`store.ps1` writes on first run. Next inlines that at build time, so it has to be
on disk before the dev server starts.

## Seed data

`seed.sql` replaces `plus-backend-main/scripts/populate-db.sql`, which is stale:
it writes to the `emote`, `player_owned_emote` and `emote_package` tables that
`m20260704_000004_drop_emotes` removed, and none of its cosmetics carry a price.
The store filters on `enabled = true AND base_price IS NOT NULL`, so an unpriced
catalogue is an empty shop.

What you get: five capes (one of them a two-variant group), one emote, one
bundle, two collections, seven tags, and the player
`a5331404-0e77-440e-8bef-24c071dac1ae` as an admin owning one cape and the emote.

The cape textures are placeholders generated by `s3.ps1 -Seed`. The presigned
urls in `scripts/dev-capes.json` expired long ago and return 403. The `wowtext`
and `santaguise` emotes need a PolyCosmetics checkout and are not seeded.

## What does not work locally

- **Checkout.** `/stripe/create` needs a real `STRIPE_SECRET` and a cosmetic
  carrying a Stripe price id. Seeded cosmetics have neither, so browsing works
  and buying does not.
- **Cover rendering** is skipped when neither Chrome nor Edge is present; the
  backend records no cover and carries on.
- **`backend-1` is not a maven server.** It is an update-check API that reads
  maven metadata and advertises download urls, so it cannot back Gradle.

## The in-game store

The Wardrobe / Store / History screen is **PolyPlus**, not OneConfig. OneConfig
supplies the shell around it — its own navigation lists only Themes and
Preferences under Personalization — so rebuilding OneConfig can never change what
the store shows. A OneConfig jar contains no cosmetics classes at all.

PolyPlus reads its backend from an in-game OneConfig dropdown that defaults to
production:

```kotlin
// PolyPlusConfig.kt
@Dropdown(title = "API URL", ...)
var apiUrl: BackendUrl = BackendUrl.PRODUCTION

// BackendUrl.kt
LOCAL("http://localhost:8080")
```

`LOCAL` already points at this stack's port, and changing the dropdown fires a
callback that reconnects the websocket and refreshes the catalogue. So pointing
the in-game store at the local backend takes **no rebuild**: set
**PolyPlus → API URL → LOCAL** in game.

One thing to watch: `LOCAL` is `http://localhost:8080` while `backend.ps1` binds
`127.0.0.1:8080`. If Java resolves `localhost` to `::1` first it will not
connect; bind `0.0.0.0:8080` instead if that happens, keeping in mind it puts the
API on your network.

Build PolyPlus from source (`polyplus.ps1`) only when you want to change the mod
itself. It resolves OneConfig from `~/.m2`, so run `mod.ps1` first and keep
`deps.oneconfig` in `PolyPlus/stonecutter.properties.toml` matching the version
that published.

## Building the mod offline

`mod.ps1` publishes the OneConfig modules into `~/.m2`, and `mavenLocal()` sits
first in `build.gradle.kts`, so OneConfig resolves locally rather than from
`repo.polyfrost.org`.

Third-party dependencies still come from Maven Central and Fabric on a cold
cache. Run `mod.ps1 -Warm` once with a network connection to fill the Gradle
cache and provision the Java 21 toolchain; after that `-Offline` works.

`mod.ps1` publishes the `modules/*` projects only, and asks Gradle which those
are rather than reading directory names — `modules/dependencies` holds a
subdirectory that is not a registered project. A root-wide `publishToMavenLocal`
also walks `:minecraft:*`, eight Minecraft versions across Fabric and NeoForge,
which drags in Stonecutter and Loom and fails long before any module is
published.

## Logs and state

Under `plus-backend-main/.local/`:

- `logs/` — one log and one `.err` per service
- `pids/` — what `stop-all.ps1` reads; anything you started by hand is untouched
- `s3/local/` — the bucket, as plain files
- `seeded` — the seed marker; `seed.ps1 -Force` reapplies

Postgres is a shared container, so `stop-all.ps1` leaves it running. Stop it
yourself with `docker stop postgres`.
